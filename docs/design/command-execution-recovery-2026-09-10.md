# 命令执行与恢复：第二批实施记录

> 历史实施记录：本地套利应用已按用户要求删除；涉及套利的实现和测试不再保留。当前范围与迁移说明见[删除记录](remove-arbitrage-2026-09-10.md)。

本批落实 F05 的单笔命令恢复，并修正套利遇到拒绝结果后仍继续发单的路径。沿用 SDK → exchange → Gateway → 应用的边界。没有增加通用工作流引擎、第二张任务表或额外消息队列。

## 架构取舍

Trading 命令与 Gateway 订单保留各自身份：Trading 负责用户意图、产品、策略归属、应用账务；Gateway 负责真实订单身份、交易所交接和订单对账。两者职责不同，不能因为都有 state 和 ID 就合并。

删除了 `gateway.Client.Handoff(Command)` 这条重复派发入口。它曾在恢复时重新解释产品 payload，并可能下单。现在只有产品执行服务调用类型化 `Execute`；`Reconcile` 无论是否已拿到 Gateway ID 都只读。手动交易与套利共用 `orders.BeginExecution` 的发送资格约束，暂时保留各自的结果入账代码，避免把不同产品行为藏进带大量回调的抽象中。

PostgreSQL 的普通命令创建和带预留额度的命令创建合并到同一个事务实现。删除了检查源码中 SQL 字符串顺序的旧测试，改为真实数据库故障注入，验证最终状态和整体回滚。

## 执行规则

1. 命令、预留额度消耗和初始恢复任务同事务提交。幂等重放不重置任务、不重复消耗额度。
2. 发送之前，`BeginExecution` 以 `expected_state=accepted` 原子更新为 `uncertain`，同时安排恢复任务。只有赢得该变更的调用者能发送。并发调用、已提交命令及结果未知命令均不能再次派发。
3. 新命令默认必须在创建后 30 秒内开始发送。超时仍未开始的命令转为 failed，记录 `HANDOFF_NOT_STARTED`，由用户查看当前行情后重新下单。前端失败原因提供中英文说明。这是**开始发送的期限**，不是挂单有效期，也不会撤销已发出的限价单。
4. 恢复任务逐条领取，查询有超时，结果持久化失败会返回并记录错误。结果未知不会被当成拒单。
5. Gateway 明确拒单、返回未知执行状态，或者套利命令结果未确认时，后续腿停止。重放已创建的平仓请求只返回现有命令，不会继续发送另一腿。保留既有成交，不产生补偿订单。

这里“已开始发送”的持久标记在网络调用之前写入。因此，标记已提交但尚未真正发出网络请求时崩溃，也只能认定结果未知。这是跨数据库和 HTTP 边界无法原子提交的窗口，不能用查不到一次就判失败来掩盖。当前将持续只读对账，尚未提供人工终结这种歧义的操作界面。

30 秒是本批采用的保守默认值，未引入可配置策略矩阵。如果后续明确需要排队执行，应另行定义用户授权的执行期限，不能让重启自动恢复过时交易意图。

## 丢失响应时如何恢复

新增公开只读接口：`GET /v1/orders/by-idempotency-key/{idempotency_key}`。

- 按认证 principal 和原始下单 key 查询已有持久订单；不创建命令、不访问交易所派发接口。
- 返回原 key、account、instrument 和原订单结果；Trading 校验全部范围后才接纳身份。
- Trading 发给 Gateway 的 key 是 **Trading command ID**，不是浏览器的幂等 key；恢复沿用同一个身份。
- 404 保留 uncertain。它可能代表原请求尚在处理，也可能是旧 Gateway 尚不支持该接口，均不能触发再次下单。
- 已知 Gateway ID 时继续按该 ID 查询并校验版本；成交通过原订单范围读取和幂等入账。

OpenAPI、HTTP 路由清单和契约测试已同步。这里使用专用查找路由，避免旧服务忽略新增列表过滤参数却返回错误订单。

## 迁移和发布顺序

新增 Trading `004_command_recovery.sql`，目标 schemaVersion 为 **4**。

旧实现可能在 Trading 仍是 accepted 时已向 Gateway 发送，因此迁移把历史 accepted 归为 uncertain，补齐缺失的非终态恢复任务，不把它们误判为未发送，也不删除订单、成交或账目。

发布时先升级 Gateway 以提供只读查找接口；停止全部旧 Trading 写入实例，备份并对明确选定的 Trading 数据库运行迁移，再启动配套 Trading 和前端。不能混跑旧 Trading 写入代码：旧实现没有发送前的持久标记，可能重新引入“accepted 实际已经发送”的歧义。若从第一批之前升级，还必须遵守迁移 003 的组合账务主键约束。

此处没有实际部署或迁移项目运行中的数据库。所有数据库验证只在 `/tmp` 的隔离 PostgreSQL 16 实例内执行，测试实例在结束时关闭。旧二进制不应直接回退运行在 v4 数据库上；应向前修复，或恢复经过核对的配套备份与二进制。
