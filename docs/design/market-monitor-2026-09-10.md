# U4：独立公开行情监控与恢复

状态：已完成。应用位于 `services/monitor`，入口为 `cmd/gateway-monitor`。使用方式见
[监控指南](../guides/gateway-monitor.md)及[中文镜像](../zh-CN/guides/gateway-monitor.md)。

## 交付与边界

监控只依赖 `clients/gateway` 和中立协议，不导入 Trader、Gateway 实现、exchange
或 SDK。一个 WebSocket 订阅有限标的的 BBO；没有第二套交易所采集、数据库、规则
语言、页面、订单执行或外部通知渠道。导入边界有回归门禁。

价格采用买一/卖一中间价，相对窗口内最早保留报价计算涨跌幅。每秒保留首条报价，
每条收到的有效报价参与判断；最少样本数按不同 UTC 秒计数。窗口是最大回看年龄，
不足完整时长但达到最少样本时即可判断，事件携带实际时间范围。它不是标记价格、
成交价或从最高点计算的回撤。价格和阈值用 decimal，比较前不先舍入。

乱序、重复、过期、未来时间、交叉盘口及非正价格/数量均不刷新有效数据时间。
其中畸形协议数据由客户端拒绝并终止流；通过协议校验的无效观察由监控忽略。
`resync_required`、generation 切换或报价超时清空窗口。恢复事件表示新鲜报价回来，
随后重新积累样本。短重启保留仍新鲜的窗口，长重启重建；不回补缺失行情。各标的
独立计算，同一标的的涨跌共享冷却，冷却跨重启和断流保留。

本地状态用一个文件保存窗口、有效数据时间、冷却与事件序号，以及有限的待输出
批次。OS 文件锁防止同一路径被两个进程同时使用；0600 临时文件、sync、原子替换
与目录 sync 保存状态。告警先持久化再输出，崩溃重放沿用事件 ID；stdout 写出和
文件确认之间不能提供恰好一次投递保证。样本最长一秒检查点，可能丢失崩溃前未
持久化的样本。输出/存储失败停止程序，不静默丢弃错误。

## 真实使用暴露并修复的契约问题

原 Go 客户端要求所有行情主题的 sequence 连续；Market Hub 已经对高频 BBO 做了
每 50 毫秒最多一次的增量推送，但 sequence 随每条原生观察增加。这两种设计组合
后，正常合并就被客户端识别为丢包。首次 35 秒双标的验收产生 62 次中断，监控
始终无法形成窗口。原有客户端测试把 BBO 当成订单簿增量，反而固定了错误假设。

修复仅放宽 BBO 的递增序号：每条 BBO 消息本身就是完整报价，允许跳过中间观察；
重复仍忽略、generation/显式缺口仍检查。订单簿增量继续要求连续。修改共享协议
说明与 OpenAPI，补上真实 Hub → HTTP/WS handler → 独立客户端回归：501 次原生
更新合并后收到 sequence 502，客户端不重连。订单簿跳号仍有独立失败回归。

监控检查的是 Gateway 实际推送的报价，不能承诺捕捉被 50 毫秒合并省略的瞬时价格。
需要逐 tick 回放或更细粒度事故分析时，应重新明确数据保留要求，不能把当前最新
报价流宣传为无损行情日志。
