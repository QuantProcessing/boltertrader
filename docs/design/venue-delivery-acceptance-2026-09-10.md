# U5 / U6：交易所边界与单机交付验收

本记录接续 [更新计划](update-plan-2026-09-10.md)。U5、U6 已完成代码、离线回归及
完整栈恢复验收。真实生产凭证、真实交易与外部通知不在本次执行范围内。

## U5：减少重复事实

- `routeprofile.DefaultProfiles` 是 20 个产品/结算路由的唯一列表。factory 只保留
  实现标签到路由 ID 的绑定，删除两套身份转换 switch；账户、产品目录与能力投影
  从同一列表读取。契约测试逐条验证工厂、凭证描述和原生行情族都能对应。
- 凭证字段由 `credential.Registry.Schema` 提供，与 Decode 使用同一认证类型。
  删除 Trading 通过构造假凭证并尝试解码来猜字段的逻辑。
- 原生行情族、REST/WS 数据集、批量/单标的粒度、协议快照与序列能力归入 exchange。
  Gateway 继续负责运行策略、采集预算、新鲜度和连接共享。没有增加超级注册表。
- 静态支持表删除固定的 `passed` / `promoted` 等成功占位与默认 write-ready 字段；
  `trading_supported` 仅表示实现范围。测试结果记录在测试中，连接健康来自运行时，
  交易所 API 权限由交易所响应裁决。Aster 已实现的资金费支持修正为真实值。
- 删除交易页 Binance 专属错误文案分支；所有交易所统一呈现已脱敏的原因与原生代码。
- 中英文交易所接入文档补充 Bybit 路由、认证字段、共享 linear 连接的完整接入路径。

明确限制保持不变：Lighter spot 不支持交易；Nado 无纯 WS 深度快照能力；
Bitget 全市场 ticker 不冒充全市场 OI；Binance/Aster 不宣称已有全市场 OI。
接口存在和离线契约通过均不代表所有生产账户模式可用。

## U6：真实故障与可诊断结果

Trading 的真实子进程验收覆盖：创建后、认领后、HTTP 发送期间强杀、收到响应但
持久化之前、响应丢失后，以及结果持久化之后退出。每个场景再启动两次，确认恢复
只查询已有身份，不再次发送下单。Gateway 原有五个真实进程崩溃场景一并通过。

待确认订单的原因、尝试次数和下一次查询时间直接投影已有 reconciliation task，
不增加第二套恢复状态表。查询失败保留已确认的成交、数量和 Gateway 版本；交易页
可查看命令 ID、Gateway 订单 ID、最近证据和诊断时间。没有新增“认为失败并重发”操作。

最小名义金额使用精确十进制比较。限价单低于已发布限制时显示原因并禁止提交；
市价单使用估算提示，由交易所按实际成交价格做最终判断。未发布规则时不造默认数值。

单机仍采用现有 PostgreSQL、Gateway、Trading、Auth edge、Web。运行镜像包含九个
命令，补入独立行情客户端与监控；支持构建平台原生架构。删除已废弃的文件凭证仓库
初始化和健康检查。`doctor -instrument` 单独检查真实 BBO 的源时间，HTTP 就绪不代替行情。

实际演练修复了以下问题：

- Trading 数据库健康原本只在启动时设为成功；现在每次请求限时查询数据库。
- 命令行的本机代理可能覆盖 Bootstrap 为容器转换后的代理地址；Compose 启动使用
  生成配置中的地址，镜像依赖下载另有显式代理参数。
- Compose 的 PostgreSQL 测试错误地把一次性迁移当作常驻服务等待；改为数据库就绪
  后运行迁移并检查退出码。镜像源码扫描也不再误判系统文件 `/etc/services`。
- 隔离恢复脚本预选固定空闲端口，避免 Docker 的 `0` 端口在重启时重新分配。
- PostgreSQL 迁移锁测试使用同一物理连接限时获取/释放锁，避免把其他测试包正常持锁
  误报为泄漏。行情测试覆盖单交易所错误和慢消费者，另一交易所仍可持续消费。
- 实际指标发现 Hotset 的一个标的被重复登记为资金费、mark、index、OI 四类订阅，
  甚至用于现货。删除这个错误的 dataset 维度和 Hub 的闲置观察接口，改为
  `gateway_market_hot_instruments{venue,market_family}`。它表示有需求的不同标的数量，
  不表示物理连接数或某类交易所订阅已经建立。

## 最终镜像的完整栈记录

2026-09-10 在独立 Compose 项目、空账户数据库和随机生成的服务令牌下运行
`scripts/acceptance/stack_recovery.py --public-seconds 180`。镜像使用专门的
`boltertrader:u6-acceptance` / `boltertrader-web:u6-acceptance` 标签，公开访问使用
显式代理。没有替换已有用户栈的容器或镜像标签。

- 目录包含 11,473 个标的，`complete=true`，无不可用产品路由。
- 180 秒监控覆盖 Binance BTC spot、OKX BTC USDT perp，价格口径为 BBO 中点。
  验收参数：10 秒窗口、0.001% 变化阈值、至少 3 个样本、最大 5 秒间隔、10 秒冷却。
- 共输出 53 个不同事件 ID：16 个状态事件、33 个价格变化、2 个中断和 2 个恢复。
  Gateway 重启后 Binance 约 4.95 秒、OKX 约 5.28 秒恢复；最终窗口分别保留 10 和
  11 个样本。该阈值仅用于演练输出，不是交易或告警策略建议。
- Gateway 和 Trading 独立停启均恢复。禁止 Trading 数据库连接并终止已有连接时，
  Trading 返回 503 且 database 组件失败，Gateway 仍返回 200；恢复连接后 Trading
  自动就绪。整个 PostgreSQL 停机时两者均不报就绪，恢复后不需要重启应用。
- 订阅期间两个原生行情族各有 1 个 Hotset 标的；监控退出并等待 35 秒后各为 0。
  这验证消费需求已释放，不把仍在工作的共享全市场采集器当作泄漏，也不宣称所有
  交易所物理连接都关闭。
- 停止四个应用后导出三个数据库，在另外三个数据库恢复，逐库核对表数量与测试
  标记，保留 owner/ACL，并核对备份主加密密钥字节一致。
- 脚本退出码为 0、报告 `complete=true`。临时容器、数据卷、服务密钥均已清理；
  mock 浏览器与开发服务器也已关闭。

Docker 单次资源采样如下，单位 MiB。期间包含进程重启，三点采样不构成长时间
内存泄漏或负载容量证明。

| 服务 | 初始 | 订阅期间 | 退订 35 秒后 |
| --- | ---: | ---: | ---: |
| Gateway | 130.7 | 145.4 | 146.9 |
| Trading | 33.54 | 41.0 | 40.48 |
| PostgreSQL | 43.16 | 45.0 | 28.46 |
| Auth edge | 5.098 | 5.098 | 5.098 |
| Web | 14.24 | 14.25 | 14.29 |

Gateway 三次 CPU 采样分别为 1.87%、2.23%、1.53%。没有据此提前增加缓存层或拆分服务。
本地原始结果位于忽略提交的 `output/u6-final/`；仓库保留验收脚本与以上摘要。
操作步骤见中英文 [恢复手册](../guides/operations-recovery.md)，可通过
`make test-compose-recovery` 复跑；公开行情通过 `--public-seconds 180` 显式启用。

## 验证边界

九家交易所执行的是 SDK、REST/WS 转换、错误脱敏、金额/数量和关闭语义的离线回归。
公开网络持续验收只选择 Binance BTC 现货与 OKX BTC USDT 永续，不能据此宣布所有
交易所、产品或账户模式都已经完成生产验收。三分钟恢复样本不是长时间稳定性结论。
本批没有读取生产交易凭证、下单、撤单、平仓或发送外部通知。
