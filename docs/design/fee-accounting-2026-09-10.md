## 实际修复的问题

| 原行为 | 本批行为 |
| --- | --- |
| 多币种费用导致 PnL 接口整体失败 | 按币种返回 `byCurrency`，不把 BTC、BNB、USDT 相加 |
| 部分路径拒绝负手续费 | 统一为正值扣费、负值返佣，账本保留该方向 |
| OKX 原始负手续费被直接传给上层 | REST 和 WebSocket 统一转换为正成本；返佣转换为负成本 |
| OKX 订单推送把累计 `fee` 当作每次成交的费用 | 只用本次 `fillFee` / `fillFeeCcy`；缺失时返回证据错误，等待查回，不使用累计数替代 |
| 买入 1 BTC、扣除 0.001 BTC 后仍记持仓 1 BTC | 记录成交量 1 BTC、库存增量 0.999 BTC，平仓目标使用后者 |
| 手动和套利分别复制一套入账算法 | 统一调用 `accounting.RecordFills` |
| 没有估值也返回未实现盈亏 0 和净收益 | 没有估值观测时省略 `unrealizedPnl` / `netPnl` / `valuationAsOf` |
| PnL 的“快照 ID”只是进程计数器 | 删除该字段，保留账目时间和独立估值时间 |
| 前端将正费用显示成正收入，微小原币金额固定两位小数 | 展示费用对收益的有符号影响，保留十进制精度 |

费用字段的解释依据交易所正式协议：[OKX API](https://app.okx.com/docs-v5/en/)、[Bybit 成交协议](https://bybit-exchange.github.io/docs/v5/order/execution)。费用币种取返回的事实，不能靠买卖方向或交易对字符串猜测。Bybit 保留 `feeCurrency`，兼容 `feeCoin` 字段；两者同时出现且冲突时拒绝该记录。

Bitget V3 的 `feeDetail` 原来只读第一项，现将同币种费用项精确相加；同一成交出现多个费用币种会明确返回 unsupported。参见 [Bitget V3 订单及成交示例](https://www.bitget.com/zh-CN/docs/catalog/trading/order-management)。Bybit 非空地区附加费用同样明确返回 unsupported，避免悄悄少记税费。这里尚未实现“一个成交对应多种费用资产”的完整模型。

## 依赖与事实边界

```text
sdk：交易所原字段
  ↓
exchange：标准成交量、成交价、带符号费用、费用币种
  ↓
Gateway：账户/订单/品种归属 + 已解析的 product、base_asset、settlement_asset
  ↓
Trading orders：保存、合并不可变成交证据
  ↓
manual → accounting.RecordFills → portfolio + ledger
```

`accounting` 只是共享入账函数，不持有订单状态，不调交易所，不自动重试网络下单。`portfolio` 管策略持仓数量和成本，`ledger` 管带币种的费用与收益记录；两者没有反向依赖。HTTP 负责给读取结果附上已有的旧账核对状态，计算与执行规则仍在应用服务中。

Gateway 成交响应新增 `product`、`base_asset`，来自已解析的品种目录。Trading 的直接执行、撤单查询、后台只读恢复均保留这两个字段。恢复从持久化 payload 读取原始品种；每条成交的 account、instrument、Gateway order ID 必须与查询一致。不能把其它订单的成交混入当前策略。

订单证据可以补充原来缺少的品种信息，但不能覆盖已有信息或修改数量、价格、手续费、币种。投影去重仍使用 principal/account/instrument/fill ID。已经完成的持仓提交可以与尚未成功的账本提交分别恢复：重放同一成交会拿回原始计算结果，不再次扣库存；缺少的费用/收益行继续按固定身份补齐。

## 数量、成本与收益

现货库存增量：

```text
signedGross = 买入 quantity / 卖出 -quantity
inventoryDelta = signedGross - fee（仅当 feeCurrency == baseAsset）
```

返佣为负费，所以基础币返佣增加库存。第三种代币或报价币费用不会改变该交易对的基础币数量；永续保证金币费用不改变合约数量。缺少品种上下文且费用是非结算币时，不能证明其对数量的影响，拒绝自动计算。

gross fill quantity 保持不变，用于检查订单是否全部成交；现货净库存另行扣除基础币手续费。
例如买入 1 BTC 并扣 0.001 BTC，订单成交数量为 1 BTC，持仓增加 0.999 BTC。

基础币费用是一笔额外库存变动，使用该次观察到的成交价计算其处置损益，费用本身仍单独记原币种账。不同时把费用资本化到平均成本后再从收益扣一遍。例如持有 1.01 BTC、均价 80，卖出 1 BTC @100 并另付 0.01 BTC：库存归零，处置毛收益 20.2 USDT，费用 0.01 BTC；按成交时 100 估价，对应净结果 19.2 USDT，与现金收支一致。此例说明计算规则，接口没有据此自动折算所有费用币种。

每个币种返回：

```text
bookedNetPnl = realizedPnl + funding - fees
netPnl = bookedNetPnl + unrealizedPnl（仅有估值观测时）
```

`byCurrency` 按币种排序，`asOf` 表示账目/观测的最近时间，`valuationAsOf` 独立表示估值时间。原币种行不是统一计价的总收益，也不是账户可用余额。没有新增资金费实际流水归因或行情到估值的连接，旧估值的新鲜度也不能仅凭存在 `netPnl` 判断；这属于 F07。

## 旧账与迁移

Trading 新增 `006_fee_inventory_context.sql`，目标 schemaVersion 为 **6**。为成交增加品种信息列，为持仓增加 `accounting_status`。

旧版本没有保存 product/base asset，且 OKX 费用方向可能错误。迁移遇到非零非结算币费用或旧 OKX 费用时，将对应策略持仓标为 `legacy_fee_review`。它不改数量、不翻转旧金额、不改原始哈希、不重写订单证据或账本。即使某笔实际上是第三币费用，也宁可保留待核对状态，不能从符号猜测。

- 新成交可以正确进入库存；安全的旧零费用/结算币费用成交允许补充元数据后幂等重放。
- 旧基础币费用不能通过重复 ApplyFill 修正，必须显式核对并重建；本批未提供自动清标或历史重建工具。
- 有待核对持仓的 lineage 不自动生成平仓数量；新成交不能覆盖该状态。
- PnL 读取返回 `409 ACCOUNTING_REVIEW_REQUIRED`，不会将待核对旧账包装成已确认收益。
- Ledger 读取仍返回原始金额，同时按完整策略归属附上核对状态；前端显示“账目待核对”，不把旧负手续费擅自解释为返佣或收入。
- 数据库读取失败返回服务不可用，不伪装成用户输入校验失败。

HTTP 契约标识升级至 **v5**：PnL 从标量改成 `byCurrency`，删去无真实快照含义的 ID；公开成交资源新增品种信息。旧 Trading 使用严格解码，不能与新 Gateway 随意混跑。发布应停止旧写入实例，备份并核对目标数据库，执行独立迁移，再启动配套 Gateway、Trading 和前端。不能只回退旧二进制重读新账务状态。

本次只迁移 `/tmp` 的隔离 PostgreSQL 16 测试实例。没有操作项目运行中的数据库、读取交易凭据、部署服务或执行实盘订单。
